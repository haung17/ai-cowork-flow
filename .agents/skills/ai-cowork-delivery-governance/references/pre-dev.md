# 開發前：需求釐清、QA / 技術評估、SOW、客戶確認、排程

## 目標

在對外確認 SOW / 報價 / 交期之前，先把需求、測試風險、技術可行性、工時估算整理清楚。

**核心原則：QA 與工程師評估完成後，才能讓客戶確認 SOW / 報價。**

---

## 主流程（10 節點）

### 1. PM 人工：需求訪談

**為什麼**：AI 可整理文字，但無法替 PM 感知客戶的隱性需求、情緒壓力與商業背景。

輸入：客戶需求陳述
工作：
- 確認專案目標與成功標準
- 識別主要使用者角色
- 記錄商業規則與限制
- 確認預算範圍與交期期望

AI 可做：整理訪談紀錄草稿、生成待確認事項清單
**PM 必須親自做**：與客戶實際溝通、判斷隱性需求、確認商務優先序

常見失敗模式：
- PM 讓 AI 直接產需求文件，跳過與客戶核實 → 後期需求偏差
- 訪談只談功能，沒談驗收標準 → 驗收時爭議

---

### 2. PM + Cowork：會議紀錄與需求整理

**為什麼**：訪談錄音 / 逐字稿通常雜亂，需整理為可執行需求文件。

Cowork 可產出：
- 需求清單（功能 / 非功能）
- User Story 初稿（As a…, I want…, So that…）
- 驗收條件初稿（Given/When/Then）
- 待確認事項 / Open Questions 清單

**PM 必須親自做**：確認語意正確、補充驗收條件、標記需求優先序、核實 Open Questions

---

### 3. QA + Cowork：測試案例 / 測試策略初稿

**為什麼**：QA 若在 SOW 確認後才介入，可能發現測試範圍遠超預期，導致工時爆掉。

Cowork 可產出：
- 正常流程測試案例清單
- 異常流程 / 邊界值測試案例
- 權限 / 角色測試案例
- 測試資料需求清單
- 高風險功能初判

**QA 必須親自做**：確認測試策略（手測 vs 自動化比例）、判斷高風險功能、確認環境需求、估算測試工時

常見失敗模式：
- QA 不在開發前介入 → SOW 低估測試成本
- 測試策略太晚確認 → 測試環境 / 資料準備不足

---

### 4. 工程師 + Claude Code：技術評估與任務拆分

**為什麼**：在報價前確認技術可行性與工時，是接案成本控制的關鍵。

Claude Code 可產出：
- API 影響分析草稿
- DB Schema 草稿
- 技術風險清單初稿
- 任務拆分草稿（task breakdown）
- 工時估算初稿

**工程師必須親自做**：確認技術可行性、校正工時估算、識別依賴關係與技術風險、確認第三方 API 限制

常見失敗模式：
- 讓 Claude Code 直接給工時估算而不核實 → 估算失準
- 技術評估只看 happy path，忽略 migration / rollback 成本

---

### 5. PM + Cowork：SOW / 報價初稿

**為什麼**：SOW 必須在 QA 與工程師評估之後才能起草，否則報價依據不足。

Cowork 可產出：
- 工作說明書（SOW）初稿
- 報價項目拆分清單
- 風險與依賴說明初稿
- 交付假設清單

**PM 必須親自做**：確認範圍措辭、設定商務條件、審核交付假設是否合理、補充不在範圍項目

常見失敗模式：
- SOW 沒有「不在範圍」清單 → 客戶誤以為功能無限
- 交付假設沒寫清楚 → 客戶環境問題反過來要求補修

---

### 6. PM 人工：內部確認與優先序

**為什麼**：在與客戶確認前，PM 需要在內部決定第一期 / 第二期切分，避免對外承諾超出實際能力。

工作：
- 確認功能優先序（必做 / 可選 / 二期）
- 識別高風險功能，決定是否預告客戶
- 確認第一期驗收方向
- 確認 PM / QA / 工程師工時是否 align

**AI 可協助**：提供功能優先序建議；但最終決策必須 PM 人工做

---

### 7. 客戶 Gate 1：SOW / 報價 / 交期確認

**為什麼**：這是開發前唯一的客戶 Gate，必須正式確認後才能安排排程。

必要輸入（Gate 進入前提）：
- 需求整理完成
- QA 測試策略確認
- 工程師技術評估完成
- SOW 初稿 PM 內部審核完畢

Gate 輸出：
- 客戶簽核 SOW（範圍確認）
- 報價確認（含付款條件）
- 交期確認（含里程碑節點）

**完成後鎖定**：SOW 範圍、報價、主要交期節點。後續變更須走 Change Request。

---

### 8. PM 人工：排程與里程碑

**為什麼**：客戶確認後才能正式分配資源、排程、設立溝通頻率。

工作：
- 依 Sprint 或里程碑排任務
- 分派 PM / QA / 工程師工作
- 設立階段交付節點
- 確認溝通節奏（週報 / Demo 頻率）

---

### 9. 工程師 + Claude Code：初始化專案 CLAUDE.md

**為什麼**：CLAUDE.md 是 Claude Code 在該專案工作的「規則書」，越早寫越穩。

Claude Code 可產出：
- CLAUDE.md 初稿（含 Coding Style、Commit 規範、測試規範）

**工程師必須親自做**：確認架構決策記錄（ADR）、補充專案特有規範、驗證常用指令正確性

---

### 10. 工程師 人工：技術確認

**為什麼**：正式進入開發前最後一道關卡，確認架構 / 依賴 / 風險與估算是否仍合理。

工作：
- 確認架構方向
- 確認依賴套件 / 第三方服務
- 重新校正工時估算（若有發現新風險）
- 若估算差異過大 → **觸發回饋線**

---

## 回饋線：何時回到 SOW 修正

以下 4 種情況，流程應回到「修正 SOW / 報價 → 客戶重新確認」：

1. 工程師技術評估後，工時估算與 PM 報價差異 > 20%
2. QA 確認測試範圍後，測試工時明顯超出預算
3. 技術評估發現 API / DB 依賴比預期複雜（第三方限制、資料遷移成本）
4. 需求整理後，範圍比訪談時大幅擴大

回到修正時：PM 說明差異原因、提出調整方案（範圍縮減 or 報價調整）→ 客戶重新確認。
