# 問題分類（Issue Triage）

## 核心原則

QA 驗證後出現的問題必須正確分類，才能走對應的處理路徑。分類錯誤是接案常見的虧損和爭議來源。

四種分類：
- **A. Bug / 未達驗收條件** → 工程師修正，不需 Gate
- **B. 需求不清 / 規格疑義** → PM 釐清，不一定走 CR
- **C. 新增需求 / 範疇變更** → 必須走 Change Request Gate
- **D. 通過 / 符合驗收條件** → 進入 Demo / UAT 準備

---

## A. Bug / 未達驗收條件

### 判定準則

以下任一成立即屬於 Bug：
- 功能的行為與原 SOW 驗收條件不符
- 系統在正常操作下產生錯誤（500、crash、資料遺失）
- 功能在 SOW 列明的使用情境下無法正常運作
- 前一版本正常、本版本出現的 regression

### 處理路徑

```
Bug 確認 → 工程師修正 → 更新 PR → CI → Code Review → Merge → 部署測試環境 → QA 再次驗證
```

**不需要**：客戶確認、Change Request、SOW 修訂

### 實例

- 按下「送出」按鈕後頁面空白，但驗收條件要求顯示成功訊息 → Bug
- 匯出 CSV 欄位順序錯誤，SOW 有指定格式 → Bug
- 手機版頁面版型破版（SOW 要求支援手機） → Bug

---

## B. 需求不清 / 規格疑義

### 判定準則

以下任一成立即屬於規格疑義：
- 需求文件未明確定義該行為，雙方理解不同
- 驗收條件描述模糊，可被解讀成多種行為
- 開發時依照某種理解實作，QA 依另一種理解測試

### 處理路徑

```
QA 標記疑義 → PM 釐清（查需求文件 / 詢問客戶） → 確認正確行為 → 更新需求文件 / 驗收條件 → QA 重新驗證
```

**是否需要 CR**：
- 釐清後，行為符合原始需求意圖 → **不需要 CR**，直接更新文件並修正
- 釐清後，發現原本就沒有這個需求 → **屬於新增需求，走 CR**

### 實例

- 「列表應依日期排序」——沒寫升序或降序 → 規格疑義
- 「管理員可以刪除用戶」——沒定義刪除是軟刪除或硬刪除 → 規格疑義
- 搜尋結果是否包含已停用的資料，SOW 未說明 → 規格疑義

---

## C. 新增需求 / 範疇變更

### 判定準則

以下任一成立即屬於新增需求，**必須走 Change Request**：
- 原 SOW 功能清單未列入的功能
- 驗收條件以外、額外要求的行為
- 系統整合方式改變（新的 API、資料格式）
- 效能、安全、可用性的新要求（不在 SOW 內）
- 任何「之前沒說，現在要求」的功能

### 處理路徑

```
識別為範疇變更 → PM 記錄 CR 內容 → 影響分析（工時 / 排程 / 報價） → 客戶確認 Gate（CR 簽核） → 更新 Backlog / 排程 → 工程師排入開發
```

**嚴格執行**：口頭同意不算。沒有書面 CR 不開發。

### 實例

- 「可以加一個 email 通知嗎？」（SOW 沒有通知功能） → 新增需求
- 「可以讓手機版也可以上傳圖片嗎？」（SOW 只說 PC 版支援上傳） → 新增需求
- 「可以匯出 PDF 嗎？」（SOW 只有 CSV） → 新增需求

---

## D. 通過 / 符合驗收條件

### 判定準則

以下全部成立即可標記通過：
- 所有驗收條件逐一確認符合
- 沒有未解決的 Bug（P1 / P2）
- 無新增需求 / 規格疑義待釐清

### 處理路徑

```
QA 確認通過 → 記錄通過清單 → PM 確認 → 進入 Sprint Demo 準備 / UAT 準備
```

---

## 最常見的分類錯誤

### 錯誤 1：新增需求被當 Bug 免費修

**情境**：客戶說「這個功能有問題」，PM 沒仔細分辨，直接叫工程師修。

**實際情況**：原始 SOW 根本沒有這個功能，客戶是想新增。

**後果**：工程師做了沒有報酬的工作，下次客戶繼續用相同方式要求。

**防範**：每個問題都對照 SOW 驗收條件確認，不在 SOW 內的一律走 CR。

---

### 錯誤 2：規格疑義被當新增需求要求加錢

**情境**：工程師說「這不在我理解的範圍內，要加錢」，但需求文件其實有暗示該行為。

**實際情況**：需求文件描述模糊，雙方理解不同，屬於規格疑義而非新需求。

**後果**：客戶認為工程師在找藉口加收費用，信任受損。

**防範**：PM 先查需求文件原文，確認是否有任何依據，再決定是 CR 還是釐清。

---

### 錯誤 3：Bug 被當規格爭議拖延

**情境**：QA 回報 Bug，工程師說「這不是 Bug，這是設計」，但驗收條件其實寫清楚了。

**實際情況**：驗收條件已指定行為，系統未達標 = Bug。

**後果**：Bug 被拖延修正，UAT 時客戶回報同樣問題，壓縮上線時間。

**防範**：回到驗收條件原文，用文字對照，不用主觀判斷。

---

## 分類決策樹（快速參考）

```
問題出現
  ↓
SOW 驗收條件有明確定義此行為嗎？
  ├─ 是，但系統行為不符 → A. Bug
  ├─ 有描述但模糊，雙方理解不同 → B. 規格疑義
  ├─ 沒有，SOW 未列入 → C. 新增需求（走 CR）
  └─ 有，且系統行為符合 → D. 通過
```
