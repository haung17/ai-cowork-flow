# 開發後：版本凍結、UAT、部署、文件交付、知識移轉、保固

## 目標

版本凍結 → UAT 環境部署 → 內部 Smoke Test → 客戶 UAT → 正式簽收 → 生產部署 → 文件交付 → 知識移轉 → 進入保固期。

**核心原則：客戶 UAT 前必須完成版本凍結、UAT 環境部署、內部 Smoke Test，確保客戶測到的是穩定版本。**

---

## 主流程（12 節點）

### 1. 工程師 人工：版本凍結

**為什麼**：不凍結版本就讓客戶驗收，會發生一邊 UAT 一邊改功能，導致驗收結果失真。

版本凍結三層次：
- **Feature Freeze**：不再合併新功能到待驗收 branch
- **Code Freeze**：只允許 bug fix，不允許重構或優化
- **Release Freeze**：環境設定、dependency 鎖定，不允許任何變更

工作：
- 確認驗收版本號（semantic versioning or commit hash）
- 建立 release branch 或 tag
- 通知 QA 和 PM 版本已凍結

---

### 2. 工程師 人工：部署 UAT 環境

**為什麼**：UAT 環境品質直接影響驗收效率，環境不穩會讓客戶把環境問題誤認為系統問題。

UAT 環境要件：
- 盡量接近 Production 環境（相同 OS、DB 版本、套件版本）
- 有完整的測試資料（覆蓋主要使用情境）
- 有 rollback point（確認回到前一版本的方式）
- 環境 URL / 帳號 / 設定提供給客戶和 QA

UAT 部署 vs 正式部署差異：

| 項目 | UAT 部署 | 正式部署 |
|---|---|---|
| 目的 | 讓客戶驗收 | 真實上線服務 |
| 資料 | 測試資料 | 實際生產資料 |
| 授權對象 | 客戶 UAT 人員、QA | 真實用戶 |
| 失敗處置 | 修正後重部署 | 需有回滾方案 |
| 公告需求 | 通常不需要 | 需要停機公告或維護視窗 |

---

### 3. QA 人工：Smoke Test / 環境檢查

**為什麼**：在交給客戶前，QA 先確認基本功能可用，避免客戶一打開就遇到低級問題。

Smoke Test 必檢項目：
- 登入 / 登出（各角色）
- 主要查詢 / 列表頁載入
- 主流程表單送出（新增 / 編輯 / 刪除）
- 付款 / 結帳流程（如適用）
- 匯出 / 下載功能（如適用）
- Email / 通知送出（如適用）
- 權限控制（角色不同，功能可見性不同）

Smoke Test 不通過 → 工程師修正 → 重新部署 → 再次 Smoke Test（**不讓客戶 UAT**）

---

### 4. 客戶 Gate 3：UAT 驗收

**為什麼**：這是開發後的第一個客戶 Gate，也是責任切分的重要節點。

UAT 進入前提（必須全部完成）：
- 版本已凍結
- UAT 環境已部署
- QA Smoke Test 通過

UAT 驗收標準：
- 依照原 SOW 功能清單逐一驗收
- 依照需求文件驗收條件確認
- 不額外新增未在 SOW 內的驗收要求

客戶回報問題時，QA 協助分類（Bug / 操作問題 / 新需求），見 `references/issue-triage.md`。

---

### 5. UAT 是否通過？（條件判斷）

- **否** → 工程師修正 → 重新部署 UAT → QA Smoke Test → 客戶重新驗收
- **是** → 進入正式簽收 / 上線同意

修正後**不可直接丟給客戶**，必須先經過 QA Smoke Test。

---

### 6. 工程師 + Claude Code：UAT 修正 / 重新部署

Claude Code 可輔助：Bug 修正、更新 PR、修正後測試補強
**工程師必須親自做**：確認修正方向、確認不引入新問題、部署確認

---

### 7. 客戶 Gate 4：正式簽收 / 上線同意

**為什麼**：正式簽收是接案責任切分的法律 / 商務節點，連動保固起算與結案條件。

Gate 輸出：
- 客戶簽收確認文件（email / 書面 / 系統簽核）
- 上線同意（確認上線時間）
- 保固起算日確認

**完成後鎖定**：UAT 版本的驗收結論、保固責任範圍、結案條件。

---

### 8. 工程師 人工：正式部署 / 回滾準備

**為什麼**：Production 部署影響真實用戶，必須有人工決策與回滾方案。

工作：
- Production 部署（可用 pipeline 輔助，但啟動需人工）
- DB migration 執行（事前備份）
- 版本 tag 建立
- 回滾方案確認（前一版本 artifact 保留、DB rollback script）

**AI 不應做**：自動決定 Production 部署時機或執行 Production 變更。

---

### 9. QA 人工：上線後 Smoke Test / 基本監控

**為什麼**：Production 環境與 UAT 環境可能仍有差異，部署後需再確認。

上線後必檢項（同 Smoke Test 清單，但針對 Production）：
- 關鍵流程可正常運作
- 服務回應時間在可接受範圍
- 已知問題是否在 Production 重現
- 錯誤監控 / 告警是否正常

---

### 10. PM + Cowork：Release Note 與交付文件初稿

Cowork 可輔助：
- Release Note 草稿（新增功能、修復項目、已知問題）
- 操作手冊初稿
- 結案摘要
- 交付清單

**PM 必須親自做**：確認內容正確、補充操作說明、審核交付清單是否完整

---

### 11. 工程師 + Claude Code：技術文件與部署說明

Claude Code 可輔助：
- 架構說明文件
- API 文件（OpenAPI / Swagger）
- 環境設定說明
- DB migration script 整理
- 部署 SOP 草稿

**工程師必須親自做**：審核文件正確性、補充特殊設定說明、確認文件與實際系統一致

---

### 12. PM 人工：Knowledge Transfer / 保固交接

**為什麼**：KT 是責任移交節點，客戶必須知道後續如何回報問題、找誰、保固範圍到哪裡。

工作：
- 帳號 / 權限移交清單
- 維護聯絡窗口確認
- Bug 回報管道說明
- 保固範圍 / 期間說明
- 教育訓練安排（如需要）

保固期詳見 `references/warranty.md`。
