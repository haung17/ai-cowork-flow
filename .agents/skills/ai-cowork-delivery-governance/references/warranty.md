# 保固 / 維護期

## 核心原則

保固期不是無限制免費修改。必須明確區分問題類型，才能知道哪些在保固範圍內、哪些需要另議費用。

---

## 問題類型分類

| 類型 | 定義 | 保固內 | 說明 |
|---|---|---|---|
| 原始範圍缺陷 | 功能未達 SOW 驗收條件 | 是 | 屬於保固責任 |
| 新增需求 | 超出 SOW 範圍的功能新增 | 否 | 需走 Change Request，另議費用 |
| 操作問題 | 用戶操作錯誤、教育訓練不足 | 否 | 可提供支援，但屬教育訓練費用 |
| 環境問題 | 客戶自行管理的環境（OS、DB、伺服器）造成問題 | 否 | 客戶責任範圍 |
| 資料問題 | 資料錯誤、資料匯入問題（非系統 bug） | 否 | 需確認責任歸屬 |
| 二期擴充 | 已驗收功能的延伸、新模組 | 否 | 需重新報價 |

**判斷原則**：對照原 SOW 驗收條件。在 SOW 範圍內、但未達驗收條件的問題 = 保固範圍。

---

## SLA 分級表

| 嚴重等級 | 描述 | 回應時效 | 解決時效 | 處置方式 |
|---|---|---|---|---|
| P1 – 緊急 | 系統無法使用 / 核心功能完全失效 | 2 小時內 | 24 小時內 | 立即處理，必要時緊急上線 |
| P2 – 高 | 核心功能嚴重受影響，但有替代方案 | 4 小時內 | 3 個工作天 | 優先排入修正 |
| P3 – 中 | 一般功能異常，有替代方案 | 1 個工作天 | 5 個工作天 | 排入下個 sprint |
| P4 – 低 | 介面問題、小瑕疵、建議改善 | 2 個工作天 | 視保固期剩餘 | 保固期內統一處理或二期列入 |

---

## Bug 回報管道

**統一入口原則**：避免客戶透過 LINE / Email / 電話 / 口頭多管道回報，否則問題容易遺失或重複。

建議做法：
- 使用 Issue Tracker（GitHub Issues / Jira / Notion）作為唯一回報入口
- 提供客戶 Bug 回報表單（含問題描述、重現步驟、嚴重等級、截圖）
- PM 設立回報確認機制（回報收到 → 確認分類 → 回覆預計時效）

---

## 修復流程

保固期修 Bug 仍須走基本流程，不能直接上線：

```
客戶回報 → PM 確認 / 分類 → 工程師修正 → QA 驗證 → 部署 → 回報客戶結案
```

注意：
- 保固期 Bug 修正後，仍需 QA 至少做 Smoke Test + 該功能回歸驗證
- 不得因為「小修正」而跳過測試和部署確認

---

## 保固到期結算 Checklist

保固到期時，PM 需確認以下項目：

- [ ] 已處理問題清單（P1/P2/P3 全部關閉）
- [ ] 未處理問題清單（P4 或非保固問題）+ 客戶確認接受
- [ ] 是否有未確認責任歸屬的問題（環境 / 資料 / 操作問題待釐清）
- [ ] 客戶是否需要維護合約（保固到期後的持續服務）
- [ ] 是否進入二期擴充討論
- [ ] 歸檔：原始 SOW、需求文件、UAT 結果、驗收簽收文件、保固期問題清單
