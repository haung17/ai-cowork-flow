# v3.6 AI Cowork / Claude Code 接案交付治理流程

## Core Positioning

This is an AI-assisted freelance software delivery governance flow, not a generic development flowchart.

Applicable contexts:
- Government or education projects
- Internal enterprise systems
- Custom business systems
- Websites, admin panels, and back-office systems

Main responsibility roles:
- PM: requirements, scope, customer communication, milestones, sign-off coordination
- QA: test strategy, test execution, defect logging, acceptance validation, production verification
- Engineer: technical evaluation, implementation, code review, deployment, rollback readiness

AI tools are assistants, not accountable parties:
- Claude Cowork: helps PM/QA with整理、起草、比對、提醒
- Claude Code: helps engineers with開發、測試、PR、CI、技術文件、CLAUDE.md initialization

## Stage 1: 開發前

Goal: clarify requirements, test risk, technical feasibility, and effort before external SOW / pricing / delivery confirmation.

Key principle: QA and engineering evaluation happen before customer confirmation of SOW / pricing.

Main flow:

1. PM 人工: 需求訪談
   - Project goal, users, major features, budget, timeline
   - AI can organize notes but cannot replace PM-customer communication

2. PM Cowork: 會議紀錄與需求整理
   - Requirement list, User Story, acceptance criteria draft, open questions
   - PM verifies meaning and customer intent

3. QA Cowork: 測試案例 / 測試策略初稿
   - Happy path, abnormal flows, boundaries, permissions, test data
   - QA owns test strategy and high-risk judgment

4. Engineer Claude Code: 技術評估與任務拆分
   - Feasibility, API / DB impact, effort estimate draft, task draft
   - Engineer confirms feasibility and estimate

5. PM Cowork: SOW / 報價初稿
   - Work statement, pricing items, risks / dependencies, delivery assumptions
   - Must happen after QA and engineer evaluation

6. PM 人工: 內部確認與優先序
   - Scope split, feature priority, risk judgment, acceptance direction

7. Customer Gate: SOW / 報價 / 交期
   - Scope sign-off, pricing confirmation, delivery date confirmation

8. PM 人工: 排程與里程碑
   - Assignment, milestones, delivery points, communication cadence

9. Engineer Claude Code: 初始化專案 CLAUDE.md
   - Project context, technical rules, architecture decisions, coding style, commands

10. Engineer 人工: 技術確認
    - Architecture, risk, dependency, estimate calibration
    - If estimate changes materially, return to SOW / pricing revision

Feedback line:
- If estimate, test scope, requirement scope, API, or DB impact changes materially, return to 修正 SOW / 報價 -> 客戶重新確認.

## Stage 2: 開發中

Goal: iterate through PR, CI, Code Review, QA validation, and issue classification without mixing bugs, unclear specs, and new scope.

Key principle: CI runs before human Code Review.

Main flow:

1. Engineer Claude Code: 開發實作
   - Feature implementation, unit tests, self-check, docs/comments

2. Engineer 人工: 建立 PR
   - PR, change summary, reviewer assignment, diff check

3. CI 自動驗證
   - Build / compile, lint / code style, unit test, security scan

4. CI 是否通過？
   - No: back to engineer fix and PR update
   - Yes: human Code Review

5. Engineer 人工: Code Review / Merge
   - Human review, review response, peer review if needed, protected branch merge

6. Engineer 人工 / 自動化: 部署測試環境
   - Test deployment, version management, environment sync, testable feature list

7. QA 人工: QA 驗證
   - Functional testing, exploratory testing, regression, acceptance confirmation

8. PM / QA Cowork: 問題彙整與影響判斷
   - Defect list, priority suggestion, impact analysis, next-step suggestion

9. 問題類型？
   - A. Bug / 未達驗收條件: engineer fixes, then PR / CI / QA again
   - B. 需求不清 / 規格疑義: PM clarifies and updates requirements
   - C. 新增需求 / 範疇變更: customer Gate, backlog update, pricing/schedule change
   - D. 通過 / 符合驗收條件: Demo / UAT preparation

Recommended cadence:
- Sprint Demo every 1-2 weeks or by milestone.
- Purpose: show progress, catch requirement drift early, reduce final acceptance risk.

## Stage 3: 開發後

Goal: freeze version, deploy UAT, run internal Smoke Test, conduct customer UAT, deploy production, deliver documents, transfer knowledge, and enter warranty/maintenance.

Key principle: before UAT, complete version freeze, UAT deployment, and internal Smoke Test.

Main flow:

1. Engineer 人工: 版本凍結
2. Engineer 人工: 部署 UAT 環境
3. QA 人工: Smoke Test / 環境檢查
4. Customer Gate: UAT 驗收
5. UAT 是否通過？
   - No: fix / redeploy UAT, then QA Smoke Test again
   - Yes: formal sign-off / go-live agreement
6. Engineer Claude Code: 修正 / 重新部署 UAT
7. Customer Gate: 正式簽收 / 上線同意
8. Engineer 人工: 正式部署 / 回滾準備
9. QA 人工: 上線後 Smoke Test / 基本監控
10. PM Cowork: Release Note 與交付文件初稿
11. Engineer Claude Code: 技術文件與部署說明
12. PM 人工: Knowledge Transfer / 保固交接

## Warranty / Maintenance

Warranty is not unlimited free modification. Always distinguish:
- Defect within original scope
- New requirement
- Operation issue
- Environment issue
- Data issue
- Phase 2 expansion

Flow:
- Unified bug report channel
- SLA by severity
- Fix -> test -> verify -> deploy
- Warranty closeout and archive

## Diagram Review Checklist

- The diagram is split into 開發前 / 開發中 / 開發後.
- SOW / pricing happens after QA and engineer evaluation.
- CI happens before human Code Review.
- Issue classification separates Bug, unclear spec, new scope, and pass.
- UAT happens after version freeze, UAT deployment, and internal Smoke Test.
- Customer Gates are limited to key points, not every small issue.
- AI is marked as assistant, not accountable owner.
- Full architecture diagram is treated as overview, not the only SOP.
