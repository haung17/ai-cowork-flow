# 開發中：開發、PR、CI、Code Review、測試環境、QA、問題分流

## 目標

透過 PR、CI、Code Review、QA 驗證、問題分類四分流，讓開發持續迭代，同時避免 Bug、規格疑義、新增需求混在一起。

**核心原則：CI 在人工 Code Review 之前執行；Bug、規格疑義、新增需求必須分流處理。**

---

## 主流程（9 節點）

### 1. 工程師 + Claude Code：開發實作

Claude Code 可輔助：
- 功能實作（依 CLAUDE.md 規範）
- 單元測試產生
- 程式碼自我檢查
- 文件 / 註解更新

**工程師必須親自做**：理解並確認產出的程式碼、判斷架構影響、處理邊界案例

常見失敗模式：
- 工程師直接 commit Claude Code 產出而不審查 → 隱性 bug 上線
- 單元測試只測 happy path，忽略邊界值

---

### 2. 工程師 人工：建立 PR

**為什麼**：PR 是品質控管的第一道關卡，說明變更範圍可讓 Review 更有效率。

PR 應包含：
- **變更摘要**：這個 PR 解決了什麼問題
- **相關 issue / ticket**：對應的任務編號
- **變更類型**：feat / fix / refactor / chore
- **影響範圍**：哪些模組、API、資料庫受影響
- **測試方式**：如何驗證這個變更
- **回滾方式**：如果出問題怎麼還原

Claude Code 可輔助：PR 描述初稿、Changelog 草稿
**工程師必須親自做**：確認影響範圍、決定 Reviewer、確認 diff 正確

---

### 3. CI 自動驗證

**為什麼**：CI 先擋掉基本錯誤，避免 Reviewer 浪費時間在可自動發現的問題上。

CI 最低應 block 的項目：
- Build / Compile（編譯失敗直接擋）
- Lint / Code Style（格式不符擋）
- Unit Test（測試失敗擋）
- Security Scan（已知漏洞警告）
- Test Coverage Threshold（覆蓋率低於門檻擋）

CI 不通過 → 回到工程師修正，**不進入 Code Review**。

---

### 4. CI 是否通過？（條件判斷）

- **否** → 工程師修正 → 更新 PR → 重新觸發 CI
- **是** → 進入人工 Code Review

---

### 5. 工程師 人工：Code Review / Merge

**為什麼**：AI 可提供 Review 建議，但合併決策必須人工負責。

Code Review 必看 5 點：
1. **正確性**：邏輯是否實作正確、邊界案例是否處理
2. **安全性**：input validation、SQL injection、XSS、敏感資料洩漏
3. **可維護性**：命名是否清楚、函式是否太長、耦合是否過高
4. **測試品質**：測試是否覆蓋主要情境、測試是否可讀
5. **影響範圍**：這個變更是否影響未在 PR 描述中提及的功能

合併保護分支（main / develop）前，所有 Review 意見應 resolved。

---

### 6. 工程師 人工 / 自動化：部署測試環境

**為什麼**：QA 需要穩定的測試環境才能有效驗證。

工作：
- 部署到 staging / testing 環境
- 確認版號管理（tag 或版本號）
- 同步測試環境設定（env variables、feature flags）
- 提供「待測功能清單」給 QA

自動化程度：pipeline 可自動部署，但 DB migration、環境差異需工程師手動確認。

---

### 7. QA 人工：QA 驗證

**為什麼**：自動化測試無法替代 QA 對需求符合度的判斷與探索測試。

QA 工作：
- 功能測試（依測試案例）
- 探索測試（找出未預期問題）
- 回歸驗證（確認舊功能未被影響）
- 驗收條件逐一確認

常見失敗模式：
- QA 只跑 regression，不做探索測試 → 漏掉新功能邊界案例
- QA 未對照 SOW 驗收條件 → 通過的東西客戶 UAT 時仍不滿意

---

### 8. PM / QA + Cowork：問題彙整與影響判斷

Cowork 可輔助：
- 缺陷清單整理
- 優先級建議
- 影響範圍分析
- 下一步行動建議

**PM / QA 必須親自做**：最終優先序判斷、決定是否進入分類節點

---

### 9. 問題類型分流（核心決策節點）

詳細處理路徑見 `references/issue-triage.md`。

| 分類 | 處理路徑 |
|---|---|
| A. Bug / 未達驗收條件 | 工程師修正 → PR → CI → QA |
| B. 需求不清 / 規格疑義 | PM 釐清 → 更新需求文件 → QA 重新驗證 |
| C. 新增需求 / 範疇變更 | **必須走 Change Request Gate** |
| D. 通過 / 符合驗收條件 | 進入 Sprint Demo / UAT 準備 |

---

## Sprint Demo 節奏

建議每 1–2 週或依里程碑安排一次 Sprint Demo。

目的：
- 讓客戶 / 內部利害關係人定期看到成果
- 及早發現需求偏差（比等到 UAT 才爆便宜得多）
- 降低最後驗收時一次爆出大量問題的風險

Sprint Demo 不是 Gate（不需要客戶正式簽核），但應記錄客戶反饋。
