AI Cowork / Claude Code

接案軟體開發交付治理流程 v3.8

PM / QA / 工程師三角色下，AI 如何介入整理、開發、測試、驗收與保固交接

2026-05-12

核心定位

不是而是適用情境
單純的開發流程圖 AI 輔助下的接案軟體開發交付治理流程 政府教育部案、企業內部系統、客製化系統、網站或後台系統
  • 流程以 PM、QA、工程師三個責任角色為主。
  • Claude Cowork 輔助 PM / QA 做整理、起草、比對、提醒。
  • Claude Code 輔助工程師做開發、測試、PR、CI、技術文件與專案初始化。
  • AI 不是責任主體，最後判斷仍由人承擔。

開發前流程

需求釐清 → 測試規劃 / 技術評估 → SOW / 報價 → 客戶確認 → 排程

開發前重點

順序責任角色重點
1-2PM + Cowork需求訪談、會議紀錄、User Story、驗收條件初稿、未確認事項。
3QA + Cowork先產測試案例 / 測試策略初稿，提前看見測試風險。
4工程師 + Claude Code技術可行性、API / DB 影響、工時估算、任務拆分。
5-7PM + 客戶 GateQA 與工程師評估後，才產 SOW / 報價並讓客戶確認。
8-10PM + 工程師排程、里程碑、CLAUDE.md 初始化、正式開發前技術確認。

開發前最重要的原則：不能先讓客戶確認價格，後面才發現技術或測試成本爆掉。小圖為了可讀性壓縮成 9 個節點；全架構圖與 dashboard 詳表保留第 10 點「工程師人工：技術確認」。

開發中流程

PR → CI → Code Review → 測試環境 → QA → 問題分類與變更控管

開發中問題分類

分類流向原則
Bug / 未達驗收條件回工程師修正，再跑 PR / CI / QA原承諾範圍內修正，通常不需客戶重新簽核。
需求不清 / 規格疑義回 PM 釐清需求必要時找客戶確認，但不一定需要更新 SOW。
新增需求 / 範疇變更進入客戶 Gate更新 backlog、調整報價 / 排程，必要時修正 SOW。
通過 / 符合驗收條件進入 Demo / UAT 準備確認階段成果，銜接開發後流程。

CI 要在人工 Code Review 前先跑，避免 Review 浪費在基本錯誤上。

開發後流程

版本凍結 → UAT 環境 → Smoke Test → UAT → 正式部署 → 文件交付 → 保固交接

開發後重點

  • UAT 前先完成版本凍結，確認客戶測的是哪一個版本。
  • UAT 環境要接近正式環境，並保留測試資料與回滾點。
  • 交給客戶 UAT 前，QA 先做 Smoke Test / 環境檢查。
  • UAT 未通過時，修正後要先回 QA Smoke Test，再交給客戶重驗。
  • 正式部署後要做上線後 Smoke Test、基本監控、文件交付與 KT / 保固交接。

保固 / 維護期

項目重點
Bug 回報管道統一入口，避免 LINE、Email、電話、口頭訊息分散造成追蹤混亂。
回應 SLA依嚴重程度設定時效，例如系統無法使用、核心功能錯誤、一般操作問題、改善建議。
修復流程保固期修 Bug 仍要走修復、測試、驗證、部署，不直接修完就上線。
保固到期結算確認已處理問題、非保固項目、維護合約或二期擴充需求。

完整 SLA / 保固分類請看 dashboard 與 skill reference。

Cowork vs Claude Code

工具適合任務定位
Cowork會議紀錄、需求整理、SOW 初稿、測試案例初稿、Release Note、操作手冊、結案摘要、交付清單PM / QA 的文件與分析助手。
Claude Code程式開發、CI / CD 輔助、技術評估、任務拆分、文件生成、CLAUDE.md 初始化、測試補強、Bug 修正、PR 協助工程師的開發與技術文件助手。

兩者都能加速產出，但責任邊界不同：Cowork 不做商務與品質決策，Claude Code 不做正式部署與架構決策。

目前版本的優點

  • 三階段架構清楚，符合一般接案公司交付流程。
  • 客戶 Gate 收斂到 SOW / 報價、Change Request、UAT、正式簽收等關鍵點。
  • 開發前已修正成先做 QA / 工程師評估，再產生 SOW 與報價。
  • 開發中順序符合實務：開發 → PR → CI → Code Review → 測試環境 → QA。
  • Bug、需求不清、新增需求、通過四類分流，適合接案業。
  • 開發後補上 UAT 前置流程與保固交接。
